## [Unreleased]

### Added

- **Inbox History: what agents asked and how it ended** (#687, console 1.94.0; E40.3, epic #684). An answered request used to vanish from the Inbox after two seconds. The Inbox now has **Waiting** and **History** tabs (`/inbox?tab=history`); History lists answered, declined and expired requests, newest first, with the outcome, what was given (a secret or a sign-in only as "Provided (not shown)"), when, and links to the request, its chat or its run. New route `GET /api/inbox/history` (keyset pages, `status` filter; capability `inbox.history`, CLI `questions list --all`).
- **The run trace shows the details asked before a task starts** (#686, console 1.94.0; E40.2, epic #684). A task run that waited for missing `{{Name}}` values had no step for that form, and the masked answers were stored but never shown. The form now records the step that asked and the answer step (including an expired or declined form), and the trace's question carries `answer.fields` (label and masked value; none for a sensitive field). The run page lists them under "Provided". The OpenAPI document, the SDK types, the run trace JSON Schema and the MCP manifest hashes are regenerated.
- **The chat keeps what the agent asked you, and how it ended** (#685, console 1.94.0; E40.1, epic #684). A request a chat's run made (a code, a sign-in, an approval, a choice, the details to start a task) used to disappear from the thread once answered, and the "Provided" line was lost on reload. Now a `request` message stays in the thread with the masked prompt and its outcome (Provided, Allowed, Denied, Declined, Done, Expired), read from the question when the thread is served; the message never holds a value, so a secret is never in `chat_messages`. The model's view of the thread reads the outcome too. New chat message kind `request` (migration `20261124100000_chat_request_messages`); the OpenAPI document and the SDK types list `memory` and `request`.
- **A new chat starts with your connected accounts on, and you choose how** (#680, console 1.93.0). "What's my last email" started a browser run instead of reading the mailbox the owner had just connected, because a chat only used an account switched on for that chat and nothing said it was off. **Now:** the owner's own setting **New chats** (Settings, Connections, and in every chat's settings; `connections.newChats` of the user settings) decides how a NEW chat starts: **Read and change** (the default), **Read only** or **Off**. A chat created without a list of accounts takes the owner's **active Google and Microsoft accounts** at that access; a list, even an empty one, is taken as it is. **Limits, all tested:** never an MCP server, a paused or disconnected account, or another user's; no chat that exists changes and no account connected later joins one; tasks are unchanged (off until the task lists them); a failed read of the setting is Off; and writes still ask, because a chat has only read tools and every send, create or change is a gated job. Each chat's "Accounts this chat may use" still overrides it. The invariant in `AGENTS.md`, VISION 26.9, `docs/connections.md` ("How a new chat starts"), `docs/security-connections.md` and the acceptance checklist are updated, and the pages that said nothing uses an account until told to now say what is true. Tests: `task-connections.db.spec.ts` (the default, the three modes, explicit lists, the exclusions, existing chats and tasks) and `NewChatAccounts.test.tsx`; two existing assumptions (a chat starts with none) were updated on purpose.
- **Epic E39 close-out: the connections documentation, the threat model and the acceptance checklist** (#608, epic #581; documentation and scripts only, no console version change, no behaviour change). `docs/connections.md` is now **one chapter**: accounts, labels, capabilities and defaults; the administrator's setup of the Google and Microsoft apps with the capability matrix; how tokens are kept; what the agent can do and the rules (the tool table, the gate); MCP servers and their trust model; the mail trigger; choosing files; the provider reference; limits and quotas; what is **not** offered (deleting mail and files, sending as someone else, local commands); and what has not been verified. New `docs/security-connections.md` is the threat model: for each of thirteen threats (a hostile page, a hostile email, a forged-sender trigger, a mail loop, a hostile or changed MCP server, a stolen database backup, a stolen refresh token, a hosted AI app, a wrong recipient, formulas in a spreadsheet, logs and traces, the sign-in flow, a compromised console) what stops it and what does not, each marked tested (against fakes), by design or not verified, with the residual risk in plain words. New `docs/acceptance-connections.md` is the owner's checklist: the eleven steps of the monthly payment example (connect, the task, run by hand, run from the schedule, idempotency, a failing delivery, agent tools, trigger, injection, trace and export, disconnect) with pass, fail or deferred columns, what to record and what never goes in the issue, and every point only the owner can confirm. Runbooks: operations section 11 ("A connection needs reconnecting", "A delivery keeps failing", "A trigger stopped firing", "Rotate the provider's app secret") and public-exposure section 9 (the callback, the recipient links in a split proxy, secrets, an incident). `README.md` walks the owner's example through the form. **Not verified:** no real Google or Microsoft account or MCP server was used, the decision record of #598 is still provisional, the Google file picker cannot load in production until the platform has a `script-src` seam (not yet filed), and after deploying the console each browser node needs `hexactra agent update`.
- **Connections in the console: choose accounts on tasks and chats, edit deliveries, see what was sent** (#607, console 1.92.0; E39.10; epic E39 #581). The web app now covers everything the epic's API does. **Task form:** two folded sections with a one-line summary, *Accounts the agent may use* (a Not used / Read only / Read and change choice per account, disabled with a fix link for a paused or reconnect-needed account, the "Runs without a browser" hint and the `needsBrowser` choice) and *Where the result goes* (the delivery editor: email with the confirm-the-address flow, spreadsheet row with a column mapping, **Fill from outputs** and a preview row, folder with a browser and a file-name example, webhook with its signing secret shown once; **Send a test**; move up and down; **Allow this account to …**; the three-step guided setup "Keep a record of each run" that only fills the form). Deliveries are saved after the task and a refusal never loses the task. **Chat:** *Accounts this chat may use* in Chat settings and chips above the composer; **approval cards for accounts** (email, event, row, with **Show all** and "They will be notified"), the recipient choice of **Don't ask again** (these people or anyone at their domain), and an Inbox group for approvals that wait. **Run page:** account steps in words ("Sent an email from Personal to 1 person") with masked details, the Deliveries block with where each went, its time, **Retry** and a link to the spreadsheet or folder, and "Started by an email". **Task page and list:** chips ("2 accounts", "3 deliveries", "Starts from email") and a read-only view of the accounts and deliveries. **Connections page:** *What it is used for* (used by, recent activity with no content, the approvals saved for the account); Saved approvals names an account instead of its id. **Home:** a notice when an account must be connected again. **API (minimal, for the choosers):** `GET /api/connections/{id}/files`, `GET /api/connections/{id}/files/{fileId}`, `POST /api/connections/{id}/files/picked`, `POST /api/connections/{id}/folders`, `POST /api/connections/{id}/picker` (the one route that gives the browser a short-lived token, for Google's file picker: Google only, Documents on, `no-store`, audited without the token), `GET /api/connections/{id}/activity`, `summary.deliveries` on a task and `mailTriggerId` on a run; the optional `connections.providers.google.pickerApiKey` system setting; `connections.files` in the capability registry (no MCP tool, no CLI). **Content security policy:** `frame-src https://docs.google.com` and `style-src https://www.gstatic.com` through `infra/nginx/app.d/csp/`; the picker's script host cannot be added through an include (the platform has no script-src seam), so until an upstream seam request lands the picker reports that it could not load and the dialog offers a pasted link ([docs/connections.md](docs/connections.md#choosing-files-the-picker-e3910)). `npm run ui:screens` has routes for each of these pages. See [README, Accounts and deliveries in the form](README.md#accounts-and-deliveries-in-the-form).

- **MCP servers as connections: Hexactra is an MCP client, so the agent can use any MCP server the owner adds** (#606, console 1.91.0; epic E39 #581, E39.9). The owner adds a server (Streamable HTTP only, `https`; nothing, a bearer token, a header or OAuth as the MCP authorization specification defines it) under Settings → Connections; Hexactra tests it first and keeps nothing unless it answered. **Every tool starts off**: the owner switches each one `read` (called without asking) or `write` (asks first, with "Don't ask again" per connection and tool); the server's hints only suggest. A tool whose description, schema or hints change after the owner decided is switched off and flagged until they review it, and they are told once. In a run the tools are `<label>__<tool>`, offered only to a task or chat that lists the connection (and an AI app's run only with `allowConnections`), with cleaned and capped descriptions and one fixed line that third-party text is information, not instructions; arguments are checked against the tool's own schema before any request and stripped of every credential; results are redacted, capped and wrapped as untrusted. Addresses are checked against private ranges at connect and at call time (DNS rebinding), redirects are never followed, nothing runs locally, and the administrator's switch `connections.mcp.enabled` (default **off**) and host lists apply. New: `POST /api/connections/mcp`, `GET /api/connections/mcp/status`, `GET /api/connections/{id}/tools`, `POST /api/connections/{id}/tools/refresh`, `PATCH /api/connections/{id}/tools/{toolId}`, `POST /api/connections/{id}/mcp-auth`, `GET\|PUT /api/connections/admin/mcp`, `hexactra connections tools`, a `connection_mcp_tools` table and `connections.config`, the notification `connections.mcp_tools_changed`, and the harness option `RunnerTool.strict`. The client is a small one over the console's own outbound transport, not the official SDK: no new dependency and no change to the API image size (`ajv` moves to `dependencies`). Tested against an in-process fake server; a real server has not been tried. See [docs/connections.md](docs/connections.md#mcp-servers-e399).

- **Deliveries after a run: an email with the PDF report, a signed webhook, a spreadsheet row and a file in a folder** (#603, console 1.90.0; epic E39 #581, E39.6). When a run of a task ends, its result goes where the owner said, without the owner doing anything. **Deterministic:** a queue job reads the finished run and the delivery's settings and sends; the model is not in that step, so nothing a page said can change a recipient, a destination or the content beyond the values of the run's own result and outputs. **Model:** `TaskDelivery` (what the owner configured, at most 10 per task, a `when` of `always`, `succeeded`, `failed` or `needs_attention`), `RunDelivery` (what happened for one run: status, attempts, a closed error code, safe detail; unique per run and delivery, the idempotency anchor) and `DeliveryRecipient`; migration `20261123100000_deliveries` (run `npm run prisma:migrate`), all three in the user-owned data registry; a schedule may choose among its task's deliveries (`deliveryIds` on `/api/schedules`). **Kinds:** `email` through the console's sender or a connection (`mail_send`), one message per address, with the outputs table, the result, a "what to check" line after a confirmed step, and the masked PDF, JSON trace or step pictures attached (over the size limit the message carries a signed link instead and says so); `webhook` (a Standard Webhooks signature with a per-delivery secret shown once and kept in the credential store, the platform's egress guard, `webhook-id` = `run:<runId>:delivery:<deliveryId>`); `sheet_row` (mapped columns plus a Run ID column, raw cell values, a retry or an ambiguous append checks for its own row first, `createIfMissing` makes and pins the spreadsheet); `folder` (a connection folder or the deployment's storage under the owner's prefix, templated names that never carry a path). **Recipients are fixed at setup:** an address that is not the owner's or a connection's must be confirmed once by the owner (a dialog naming it, recorded with the time) before the delivery can be on; the recipient is told once, every report carries a link that stops the emails (a page with one button, so a mail scanner changes nothing); deployment caps `maxRecipientsPerTask` (10) and `maxEmailsPerDay` (100) in the new `deliveries` system settings. **Sent once:** a run end writes the rows and queues one `deliveries.send` job each; a row is claimed compare-and-set, a job that runs twice or a hook that fires twice sends once, and a write whose outcome is unknown is checked, never repeated blindly. **Retries:** up to 5 attempts with backoff for a rate limit, a provider error or a network error; anything else (`CONNECTION_NEEDS_RECONNECT`, `CAPABILITY_OFF`, `NOT_FOUND`, `PERMISSION_MISSING`, ...) fails at once with its code and the owner is told once per task per day; a delivery failure never changes the run's status. **Masking:** a sensitive output reads `[hidden]` unless the delivery was set up to carry it, a subject or file name never carries one, and attachments are always the masked files of E35. **API:** `GET|POST /api/tasks/{id}/deliveries`, `PATCH|DELETE .../{deliveryId}`, `POST .../{deliveryId}/test` (a clearly marked test with sample values, no run read), `GET /api/runs/{id}/deliveries`, `POST /api/runs/{id}/deliveries/{id}/retry`, `GET|POST /api/delivery-recipients`, and with no session `GET /api/reports/{token}` (the masked PDF for a signed 7-day link) and the unsubscribe page. `runs.run.finished` gains, additively, `outputsComplete`, `runUrl` and `reportUrl`. **Clients:** SDK regenerated (`hx.tasks.deliveries`, `testDelivery`, `hx.runs.deliveries`, `retryDelivery`), CLI `hexactra tasks deliveries list|test` and `runs deliveries [--retry]`, the run page's **Deliveries** block with a **Retry**, MCP `run_status` reports a `deliveries` summary (counts by status) and **no MCP tool creates or changes a delivery**. **Operations:** counters `app.deliveries` and `app.deliveries.duration`, audit events `delivery.*` (ids, kinds and counts, never an address, subject, body, cell or file name), a `deliveries.failed` notification, and the alert rule `hexactra.delivery_failing`. The router's parameter length is raised to 1024 for the signed links. Not in this issue: the editor UI (E39.10), webhooks to an existing platform endpoint (the platform has no seam for one payload to one endpoint), and a check with a real account (the owner's acceptance run). [docs/deliveries.md](docs/deliveries.md).
- **Agent tools for mail, calendar and documents: the agent uses the owner's connections in a run and in a chat** (#604, console 1.88.0; epic E39 #581, E39.7). A task or a chat lists the connections it may use, each `read` or `read_write` (`connections` on `POST`/`PATCH /api/tasks` and `/api/chats`; **off until listed**; a run takes a snapshot when it starts; a run an AI app starts gets none unless the app's new limit `allowConnections` is on). The runner offers provider-neutral tools (`connections_list`, `mail_search`, `mail_read`, `mail_attachment_to_browser`, `mail_draft`, `mail_send`, `mail_modify`, `calendar_list`, `calendar_free_busy`, `calendar_create_event`, `calendar_update_event`, `calendar_delete_event`, `docs_search`, `docs_read`, `sheet_read`, `docs_create`, `docs_append`, `sheet_append_rows`, `sheet_create`, `file_upload`): every call names the account (more than one candidate becomes a question to the owner), results are marked as the owner's data and capped per run (`connectionReadMessages`, `connectionReadChars` in the agent policy's context section), and nothing deletes mail or files. Anything that sends, creates, changes or appends asks on a high-risk card the server builds from the validated call; "Don't ask again" creates the new saved-approval kind `connection` (this connection, this tool) and, for mail and invitations, only the **approved recipients**: sending to someone new always asks. A crash around a send leaves the step unknown and never repeats it. A job that needs only connections opens **no browser** (`Task.needsBrowser`: `auto` opens it at the first browser tool call when the run has connections, `always`, `never`), and the owner is asked without one: a question may now have no browser handoff. The chat answers simple questions about mail, calendar and documents itself with the read tools and starts no run. No MCP tool exposes a connection. New tables `task_connections`, `conversation_connections` and columns on `tasks`, `approval_rules`, `questions` and `connected_app_settings`: run `npm run prisma:migrate`. Docs: `docs/connections.md` ("What the agent can do with a connection"), `docs/approvals.md`, `docs/chat.md`, `docs/runner.md`, `docs/parity.md`, `docs/security-hosted-clients.md`. Not verified against a real Google or Microsoft account; `mail_attachment_to_browser` needs the browser host to accept an `upload_file` action, which it does not yet.
- **Epic E38 close-out: a harness you can stop, pause and trust** (#589, epic #580; documentation and scripts only, no console version change, no behaviour change). One summary of what the epic changed, for operators and for client authors. **New run status `paused`** (E38.2): a client that enumerates run statuses (a `switch`, a status map, a chart series, a "live" test) must handle it as a **live**, non-final, non-deletable status; the API, SDK, CLI and MCP already carry it. **New fields:** `pauseRequested`, `pausedAt`, `traceId` on a run, `phase` on a step. **New routes and tools:** `POST /api/runs/{id}/pause` and `/resume`, `hexactra runs pause|resume`, MCP `run_pause` and `run_resume`. Stop is checked before every action and aborts the model call in flight (`app.runs.stop_latency_ms`), a restart continues a run and never repeats a step the owner confirmed (`app.runs.recovered`), every job is one OpenTelemetry trace, and the agent harness is two workspace packages (`@marinoscar/hexactra-agent`, `@marinoscar/hexactra-browser-agent`) with a replay suite. Docs: `docs/runner.md` (one chapter: the parts, the life of a run, Stop, Pause, crash recovery, traces, the replay suite, how to add a tool), `docs/runs.md`, `docs/chat.md` ("Stop and Pause in a chat"), `docs/runbooks/operations.md` ("A run will not stop", "A run recovered after a restart", "Find a run's trace and read it"), and `docs/runbooks/run-harness-acceptance.md`, the procedure and results table for measuring the epic on a deployed stack. **The measurements themselves have not been taken yet:** see the acceptance runbook and #589.
- **A replay suite: check a prompt or model change against recorded runs before it ships** (#587, console 1.85.0; epic E38 #580, E38.6). Changing the agent's instructions, a tool description, a gate or a model used to be a guess. `apps/api/test/scenarios/*.scenario.json` describe a fake website (pages, elements, what a click does), what the owner answers, a scripted model and what must hold at the end; `runScenario` (the test kit in `apps/api/test/replay/`) runs the real chunk loop with the browser toolset and its gates over it, with a new job at each question, crash and pause. Seven invariants are checked on every scenario: no commit-class click without a confirmation or a saved approval, no navigation outside the allowed sites, no secret or marker string in a step, the memory, the model's input or a span, no commit repeated after an unknown step, no action after Stop or while paused, and page text never changes a recipient, an allowed site or an approval; each has a scenario that breaks it on purpose. Sixteen starter scenarios (lookup, form, login, code, confirmed and denied payment, a saved approval, a date picker, a stall that escalates, budgets on unattended and chat runs, an injection page, crashes before and after a click, Stop and Pause) run in `npm test` and as `npm run scenarios --workspace=api` (a table and JUnit XML, in CI, failing when none is found). `npm run scenarios:live` runs them N times against a real model on a chosen tier under a spend cap and writes a summary with a diff against a saved baseline (manual workflow `scenarios-live.yml`, never in the default CI job). `hexactra dev scenario-from-trace <trace.json>` makes a scenario skeleton from an exported run trace. `runner.db.spec.ts` now takes its fabric and AI fakes from the kit. Docs: runner.md, "Testing a change to the agent".
- **Email triggers: start a task when a matching email arrives** (#605; epic E39 #581, E39.8; console 1.87.0). On a task's page, **When an email arrives** (beside the schedules): pick a connected account, say who the email must come from (**required**: an exact address or one domain; a domain anybody can have an address at is refused) and what else to look for, and one run starts per matching message that arrives afterwards (trigger `email`, origin `system`). The console polls (5 minutes by default, 1 minute at least) through the provider-neutral mail interface, **re-checks every message itself**, refuses a message whose sender fails the provider's authentication check, never replays mail from before the trigger was switched on, records each message id **before** the run starts so it fires once, and stops at a per-trigger and a per-owner daily cap (a message from the account's own address never starts a run, so a run's own mail cannot loop). Task parameters can take a fixed value, a header (`subject`, `from`, `date`) or a value captured by a safe one-group pattern; they are data, they cannot change the allowed sites, confirmations, policy or recipients, and a missing value makes the run wait on the form. **The message is never in the goal**: the run gets a reference and one line saying so. `GET|POST /api/tasks/{id}/mail-triggers`, `PATCH|DELETE /api/mail-triggers/{id}`, `POST …/test` (the last 5 matches, subjects cut to 60 characters, nothing started), `GET …/events`; `hexactra tasks triggers list`; no MCP tool creates a trigger (`tasks_list` shows a count). New tables `mail_triggers` and `mail_trigger_events`, the run trigger `email`, `runs.context` and `runs.mail_trigger_id`: run `npm run prisma:migrate`. Deployment limits: the `mailTriggers` system settings. **Fails closed on the sender check:** the Google adapter now reports the receiving server's SPF, DKIM and DMARC result (`senderAuth`); a message that failed it never starts a run, and one the provider could not check starts one only when the trigger's "Also accept mail the provider could not verify" (`acceptUnverified`, off by default) is on. The Microsoft adapter must fill `senderAuth` too (see `docs/connections.md`). Not verified against a real mailbox.
- **Google provider: Gmail, Calendar and Docs, Sheets and Drive behind one provider-neutral interface** (#601, console 1.84.0; epic E39 #581, E39.3). Sign in several Google accounts (OAuth with PKCE, offline access, incremental consent that asks only for the new permission) and give the rest of the console one typed set of operations for mail, calendar and documents: `apps/api/src/connections/capabilities.ts` defines `MailCapability`, `CalendarCapability` and `DocumentsCapability` with zod schemas, a read or write tag and the capability each method needs, the limits (message text 50,000 characters, an attachment 10 MB, a sheet read 5,000 cells, a list page 50) and one typed error (`CapabilityError`: `CONNECTION_NEEDS_RECONNECT`, `CAPABILITY_OFF`, `PERMISSION_MISSING`, `NOT_FOUND`, `RATE_LIMITED`, `QUOTA_EXCEEDED`, `TOO_LARGE`, `PROVIDER_ERROR`). `ConnectionCapabilities` resolves the provider from the connection; a call without the capability fails with `CAPABILITY_OFF` before any request. **Safety rules in the adapter:** a Gmail query is built from the structured `MailQuery` and every value is quoted, so operators in a value are text; outgoing mail is composed by a small tested RFC 5322 composer (UTF-8, plain and HTML, attachments, reply threading, `From` always the connected account, a newline in any header value is refused); calendar writes notify nobody unless `notifyAttendees` is true and creating an event is idempotent; spreadsheet values are written `RAW` so `=HYPERLINK(...)` stays text; an append whose outcome is unknown is not retried and returns `ambiguous: true`. Requests use plain `fetch` over the console's SSRF-guarded transport (no Google client library, no new dependency), with per-connection concurrency, backoff with jitter on `429` and `5xx` (3 tries, `Retry-After` honoured) and an `AbortSignal`; telemetry carries operation names, sizes, counts and status codes and never a subject, address, body, file name, query or cell. **Per the decision record (E39.1) a seventh switch, `mail_modify`** (archive, labels, mark read, drafts), is added to the capabilities, the page and the CLI. `POST /api/connections/{id}/test` now runs one cheap read per capability at Google. Test doubles for later issues: `connections/testing/` (in-memory capabilities) and `connections/google/testing/` (an in-process fake of the Google endpoints). **Not verified on a real Google account yet.** Documented in `docs/connections.md` ("Google").
- **Extract the agent harness into packages: a generic harness and the Hexactra browser toolset** (#614, E38.9; no behaviour change). `packages/hexactra-agent` (`@marinoscar/hexactra-agent`: loop, tool registry, gates, budgets, checkpoints, ports, in-memory fakes and `runHarnessHostConformance`) and `packages/hexactra-browser-agent` (`@marinoscar/hexactra-browser-agent`: the browser and desktop tools, the site and risk gates, vision) are built to `dist/` and imported by the API, which keeps only the host bindings (`apps/api/src/runner/host/`) and the tools that reach console services. New scripts `build:packages`, `typecheck:packages`, `test:packages`, `check:package-pack` (run first by `build`, `typecheck` and `test` and by CI; a fresh checkout needs `npm run build:packages` after `npm ci`). Publishing is off. Docs: `docs/runner.md`, `docs/decisions/agent-packages.md`.
- **Task outputs: named values the agent returns when it finishes** (#600, console 1.83.0; epic E39 #581, E39.5). A run used to end with free text; a task can now declare the facts its owner wants to file (an amount paid, a confirmation number, a date, a remaining balance) and the agent must return them. **Definitions:** `Task.outputs` (new migration `20261121090000_task_outputs`: run `npm run prisma:migrate`), `outputs` on `POST/PATCH /api/tasks` (`{ key, label, type, required, options?, help?, sensitive? }`, at most 30, the key derived from the label, `400 INVALID_OUTPUTS`); types are the shared ones of the new `packages/shared/task-fields.js` (`text`, `number`, `money`, `date`, `datetime`, `boolean`, `url`, `choice`). A run copies the definitions when it starts (`runs.outputs_spec`), so editing the task never relabels an old run, and no start (a schedule, the API, MCP, the chat) can redefine them. **The agent:** the instructions gain a section listing the outputs (the same text every round, part of the stable prefix); `finish` gains `outputs`, its JSON schema built from the definitions (exactly the task's keys, each nullable; a task without outputs keeps today's schema). **Server-side validation:** each value is read by its type (money with a sign or code and thousands separators, dates in common local forms when unambiguous, yes/no, absolute web addresses); a success finish with a missing required value or one that does not parse is answered with what is wrong ("`amount_paid` is not an amount of money: 'ten dollars'") and the run continues, twice at most, then it ends with what it has (invalid fields `null` with their reason, `outputsComplete: false`). A failed finish is never refused and stores what it gives; the wrap-up call after a budget or a stall uses the same schema; a model that stops without `finish` is asked for the outputs by the same rule. **Storage and views:** `runs.outputs` (`{ key: { value, ok, note? } }`) and `runs.outputs_complete`; `GET /api/runs/{id}` returns `outputs` (labels and types as the run started with them) and `outputsComplete`, a list row only `outputsComplete`; new `GET /api/tasks/{id}/outputs` (keyset paged, newest first, `columns` and `items`; `404` for another user's task). ### Fixed

- **Agent runs no longer fail at step 0 with AI_INVALID_REQUEST** (#679, console 1.92.10). Right after the chat was fixed, a browser run started from it failed with no steps and no reason. The runner sends every built-in tool with strict function calling, which needs every property listed as required; `type_handoff_secret` had `parameter` as nullable AND optional, so OpenAI refused it and, with all tools in one request, the whole model call. **Now:** `parameter` is nullable and required (the description already said "otherwise null"). **A failed run names what the provider objected to**, as the chat does: `AI_INVALID_REQUEST (invalid_function_parameters, tools[N].parameters): ...` (identifiers only; the provider's message and request id never appear in the run's line), and the API logs one warn line with the platform's `aiErrorLogDetails`. **Guards:** the runner characterisation test lints every strict tool the runner offers (every switch on) against the strict subset, and the `finish` tool with outputs of every type is checked in `chat-tool-schemas.db.spec.ts`; the snapshot change is only `parameter` joining `required`.
- **The chat answers again: its memory tool no longer breaks every model call** (#675, console 1.92.7). With 1.92.5 the chat named what OpenAI refused: `invalid_function_parameters` on `tools[3].parameters`, the chat's `propose_memory`. Its `attributes` field was a free-form object, which OpenAI's strict function calling does not accept, and because every tool is sent in one request that one schema made OpenAI answer 400 to EVERY chat message, even `hello`. **Now:** `attributes` is a list of `{ name, value }` pairs (strict-valid, and how `run_task` already passes its inputs), turned back into the record the memory service takes by one helper (`memories/memory-attribute-pairs.ts`: trimmed, a blank pair dropped, a repeated name keeps its last value); the agent runner's own `propose_memory` had the same field and gets the same change (its pinned schema in the characterisation snapshot is updated on purpose, nothing else in it moved). The four chat tools with no arguments (`stop_run`, `pause_run`, `resume_run`, `draft_task`) are sent without strict mode as a precaution, because OpenAI reports one bad tool per call. **A guard so it cannot ship again:** `chat-tool-schemas.db.spec.ts` builds the chat through the real app, takes the tools it hands the model and checks every strict one (and the connection read tools and the runner's memory tool) against the strict subset (`test/helpers/strict-schema.ts`); it fails on the old free-form field and names it. Runbook: `docs/runbooks/operations.md`, "The chat answers AI_INVALID_REQUEST".
- **A chat that OpenAI rejects now says what it objected to** (#675, console 1.92.5). On the first real test of connections every chat message, even `hello`, answered "The AI could not answer (AI_INVALID_REQUEST)": OpenAI answered 400 within a second and nothing in the thread, the job or the log said why, because the platform keeps the provider's message off the error. **Now:** the owner's line carries the provider's own short code and the request field it named, identifiers only (`The AI could not answer (AI_INVALID_REQUEST: invalid_function_parameters, tools[3].parameters)`; a value that is not an identifier is left out and the provider's message never appears there), and the API logs one warn line per failed turn with the status, code, type, parameter and provider request id, plus, for a rejected request, the provider's message with keys, tokens and URLs redacted and capped (the platform's `aiErrorLogDetails`; server log only). Tests in `chat-turn.db.spec.ts`: the text with identifiers, with values that are not, with none; the log line and no leak of a marker key in the thread or the log. Runbook: `docs/runbooks/operations.md`, "The chat answers AI_INVALID_REQUEST".
- **A duplicate delivery of the Google (or Microsoft) return no longer shows an error for a connect that succeeded** (#672, console 1.92.3). On the first real phone test the owner approved every Google consent screen, saw "The connection could not be completed" and an empty list, and the account was in fact connected: the callback URL had been delivered **twice at once** (the in-app browser and the app link). The first request claimed the single-use flow and exchanged the code (1.5 s); the second found the flow gone, answered `state_invalid` after 28 ms and the page showed that. **Now:** the callback is single-flight per state: a repeat of a callback that claimed its flow (connected, denied, refused, expired, a failed exchange, ...) waits for the first and answers the **same outcome**, without the connection's id and without exchanging the code again, for two minutes (in memory, bounded to 500 states, nothing but the outcome, the return path and the missing capabilities is kept); a callback that did **not** claim the flow (another browser, an unknown state) is judged on its own, leaves nothing behind and does not stop the owner finishing; after the window a replay is `state_invalid` as before. The single-use claim, the binding cookie check and the one-time exchange are unchanged. Tests in `connections.db.spec.ts`: two concurrent callbacks exchange once and both end on connected; a replay within the window and after it; another browser's callback is not remembered; a different state is unaffected. Runbook: `docs/runbooks/operations.md`, "A connection will not complete".

- **A connect that fails now says which way and why** (#670, console 1.92.2). On the first real Google test the owner approved every consent screen, was returned to the callback and saw only "The connection could not be completed", with nothing in any log to say why. - **`hexactra deploy update` no longer fails at the last step when the api container is short of memory** (#668, console 1.92.1). - **Scope-gated MCP tools and step-up consent for OAuth apps** (#460, E33.2, console 1.42.0): an app signed in with OAuth sees and can call only the tools its consent covers, and asks the user for more when it needs it. Details: `docs/mcp.md`, "What a connected app can do" and "Asking for more".

- **Agent policies** (epic #398): named, versioned, personal bundles that say which models a run uses and how much it may spend. A policy holds model tiers, six budgets, stall detection and context settings.
  - Four built-in, read-only policies: Economy, Balanced (the default), Thorough and Unlimited. A user duplicates one to edit a copy, chooses one default, and assigns a policy to a task, a schedule or a single run ("Run with...").
  - Resolution order: the run, then the schedule, the task, the user's default and `builtin:balanced`. The policy is snapshotted onto the run at its first step, so editing it never changes a run in flight.
  - API `/api/agent-policies` (list, create, read, edit with `If-Match`, delete with `reassignTo`, duplicate, default, effective model tiers), permissions `agent_policies:read` and `agent_policies:write`. Tasks, schedules and run starts take `policyId`.
- **Model tiers**: Fast, Standard and Frontier, each a model, a reasoning effort, an output cap and an optional fallback model. Defined once per deployment (`browserAgentTiers`), overridable per user, and pinnable per policy. A run starts on the policy's start tier and escalates when it stalls, then steps back down after progress. Models change only between chunks, so provider prompt caching holds. A tier's fallback model is used on a provider error or rate limit when the policy allows it.
- **Budgets, each optionally unlimited** (`null`): actions, model calls, active minutes, input tokens, output tokens and cost. A warning reaches the model at the policy's threshold, and a used-up budget ends the run after one wrap-up call. Administrators set **ceilings** (`browserAgentCeilings`) that cap every policy, Unlimited included. Every finished run records a typed `stopReason`.
- **Stall detection**, always on: failures in a row, a repeated action, no progress and rounds with no action nudge the model, escalate a tier, ask a person or end the run as `stalled`. It keeps only digests, never typed text, secrets or images.
- **Per-run cost.** Every model call is priced from the administrator's `agentPricing` table (USD per million tokens). Runs report `modelCalls`, `cachedInputTokens`, `costUsd` and `costKnown`; tasks report their 30-day spend and the average cost of a successful run.
- **Context settings** (screenshots kept, calls per chunk, observation size, prune batch) with a stable prompt prefix, and the histogram `app.runs.input_tokens_per_call`. On the measurement fixture Balanced sends 18% fewer input tokens than the earlier fixed settings.
- **Export and import** of policies as JSON (`hexactra.agent-policies`, `formatVersion` 1), atomic, with `rename`, `skip` or `replace` on a name clash. A file holds no ids, user or secret.
- **Web**: Settings → Browser agent → Agent policies and Model tiers; Administration → Browser agent → Agent model tiers, Agent budget ceilings and Model prices; a policy picker on tasks and schedules; "Run with..."; on the run page the policy, tier and model, a live budget meter, the stop reason and routing rows; run cost in the runs list and spend on task cards.

### Changed

- **MCP, for every client** (#462): tool errors are no longer the raw REST string (`"403 FORBIDDEN: …"`) but a sentence with the code in parentheses where it helps (see `docs/mcp.md`, "Errors"); `run_status` returns the latest 20 steps by default (was 10) plus `olderSteps`; `browser_elements` returns 200 elements by default (was a fixed 80); `browser_text` returns up to 20,000 characters by default (was 8,000); results from web pages start with the untrusted notice; and on `2025-06-18` and later the text block of a structured tool starts with a summary line before the JSON (read `structuredContent` instead of parsing the text). `policies_export` is in the `runs:read` scope: it only reads.
- A run's time budget counts **active** time only. Time spent waiting for a person no longer makes a resumed run fail, and a run that outlasts one job continues in a new job.
- A run's limits come from its agent policy: the default Balanced allows 60 actions, 120 model calls, $2 and 20 active minutes (the earlier task default was 100 steps and 30 minutes). Existing tasks keep their limits through a derived `Task: <name>` policy created by the migration.
- The goal runner picks every model call's provider, model, reasoning effort and output cap from the run's resolved tiers, no longer from the task's `model` or the user's default model alone. A run with no usable model fails at once, naming the tier, before a browser is allocated.
- The documentation (`VISION.MD` sections 25 to 27, the console README, runbooks, API, security and MCP guides) describes policies instead of per-task step and time limits.

### Deprecated

- The task fields `maxSteps`, `maxMinutes` and `model`. They still work and map to a derived personal policy (`Task: <name>`), and the response carries a `Deprecation: true` header. Use `policyId` instead. **They are removed in the release after the one that introduced agent policies.**
