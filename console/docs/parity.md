# Client parity: what hosted AI apps (E33) added

What each client can do with the capabilities of epic E33 (#458): connected apps, `run_wait`, the run origin filter, the MCP activity log, the kill switch, the in-chat cards and consent. "No" is a decision with its reason; nothing here is left for later unless it names an issue. The earlier tasks, schedules and runs capabilities are in [api-tasks-runs.md](api-tasks-runs.md#client-parity). The machine-checked form is [packages/shared/capabilities.json](../packages/shared/capabilities.json): `apps/api/test/capabilities.db.spec.ts` (REST, MCP), `apps/cli/src/capabilities.test.ts` (CLI, TUI) and `apps/web/src/__tests__/capabilities.test.ts` (web) fail when a surface drops a value it names, or when a route, command or tool belongs to no capability. The registry has no Android column: the Android app is a Trusted Web Activity around the web app, so a page that exists on the web exists there (see [the Android column](#the-android-column)).

## The Android column

The Android app opens the console in a Trusted Web Activity, so every page above is there. What was **not** verified: that the consent page (`/oauth/consent`) opens inside the app when a hosted client's sign-in lands on the phone (for example, connecting from the Claude or ChatGPT mobile app), and that a tap on an `app.connected` or `app.scope_added` notification opens `/settings/ai-apps/:clientId` in the app. No device was available when E33 was closed. Until someone checks on a device, the behaviour is: the sign-in opens in whatever handles the link (the app if Android's link verification for the console's host succeeded, otherwise the browser), and either one completes the consent. A follow-up issue records the device check.
