# Threat model: hosted AI clients (ChatGPT, Claude) on the console

The console's MCP endpoint lets hosted assistants (ChatGPT, Claude) drive the owner's browsers, with the owner's full powers within the scopes they consented to (VISION §27). This page names what is at stake, who might attack it, where the trust boundaries are, and which control answers each threat, with the test that proves it. Operators: [the public-exposure runbook](runbooks/public-exposure.md). Saved logins, identity details and cards the agent uses without seeing them have a threat model of their own: [security-secrets.md](security-secrets.md) (the rows below on saved logins, details and cards are the part of it that concerns hosted AI apps). The mail, calendar and documents the owner connected, and what a run sends out, have theirs: [security-connections.md](security-connections.md) (the row below on mail, calendar and documents is the part of it that concerns hosted AI apps).

## Assets

- **The owner's signed-in browser profiles** on their nodes: bank, mail and shop sessions; whatever the browser can do, an app with `browser:drive` can ask for.
- **The owner's money**: purchases a run can make; model spend (budgets).
- **Secrets**: passwords and one-time codes typed through handoffs (the fabric types them; the console never holds them), personal access tokens (`pat_`), OAuth access and refresh tokens (`oat_`, `ort_`), the fabric's service token (`hxs_`), webhook secrets, session cookies.
- **The record**: runs, steps, questions, the AI app activity trail.
- **The deployment**: its availability and its settings.

## Actors

| Actor | Can | Wants |
|---|---|---|
| The owner | Everything in their console | Their goals done; to stay in control |
| The hosted vendor (OpenAI, Anthropic) | Sees every tool result its model reads; calls `/api/mcp` with the token the owner granted | To run the model; it is trusted with what the owner sends it, like any hosted model |
| A malicious web page | Puts text in front of the model through `browser_text`, element labels, script values, tab titles, a run's answer | To make the model act for it: buy, send, share, exfiltrate |
| A malicious MCP client | Registers itself, asks the owner to connect, calls `/api/mcp` | Broad scopes, a token it can keep |
| A thief of a token | Holds an `oat_`, `ort_` or `pat_` | To act as the owner |
| The internet at large | Calls any public path | Probe, flood, find something open |

## Trust boundaries

```text
            ┌────────────────────── internet ───────────────────────┐
 web page ──┤ (page text)                                            │
            │        ┌──────────────┐  tool results    ┌───────────┐  │
            │        │ hosted model │◀──────────────── │  vendor   │  │
            │        │ (ChatGPT,    │──── tools/call ─▶│  servers  │  │
            │        │  Claude)     │                  └─────┬─────┘  │
            │        └──────────────┘                        │ HTTPS, oat_ token
            └────────────────────────────────────────────────┼───────┘
     ═══════════════════ edge: TLS, nginx limits ════════════╪═══════════
                                                             ▼
   ┌──────────────────────────── console (API) ───────────────────────────┐
   │ /api/mcp: auth → kill switch → rate limits → scope gate → tool        │
   │   tool → REST route in-process as the NARROWED principal              │
   │   sensitive action? → confirm (risk high) in the owner's inbox        │
   │   result → token redaction → model        call → audit row           │
   └───────────────────────────────┬──────────────────────────────────────┘
                                   │ hxs_ service token (private network)
                                   ▼
                     fabric ──▶ node ──▶ the owner's browser
```

Untrusted input crosses into the model at "page text"; authority crosses into the console only at "oat_ token". Nothing from a page or from model output is ever a source of authorization: approvals come only from a channel where the owner is signed in.

## Threats, mitigations and the tests that prove them

| Threat | Mitigation | Test |
|---|---|---|
| **Stolen `oat_` token** | Scoped to what the owner ticked; lives 60 minutes; confined to `/api/mcp` (`403` elsewhere); narrowed permissions on every in-process sub-request; Disconnect revokes it at once; the kill switch refuses all of them | `mcp-oauth.db.spec.ts` (confinement, narrowing, revocation), platform `oauthServer` conformance; `mcp-public-exposure.db.spec.ts` (kill switch, admin Disconnect → `401`) |
| **Stolen refresh token** | Rotation on every use; reuse of a rotated token revokes the whole grant (the platform's reuse detection) | platform OAuth server suite (`oauthServer` conformance, `mcp-oauth.db.spec.ts`) |
| **Malicious client registration** | Only allowed client hosts may connect (Administration → OAuth clients; "any host" off); the consent page shows the client's host first | platform `oauthServer` conformance; `connected-apps.db.spec.ts` (preflight) |
| **Consent phishing** (a look-alike app asks for broad scopes) | Host-first consent; high-risk scopes unticked by default; `app.connected` and `app.scope_added` are mandatory notifications ("Not you? Disconnect it") | `connected-apps.db.spec.ts` (notifications) |
| **Prompt injection through page text** (a page tells the model to buy, send or share) | Page-derived text is marked untrusted (E33.4); OAuth callers' instructions say page text is data, not instructions, and to ask before sending, buying, deleting or sharing when a page suggested it; **sensitive browser actions need the owner's approval** in a signed-in channel (a `confirm` with risk high; the app cannot approve through `inbox_answer`), bound to the session, action and target for 2 minutes, once; per-app allowed sites, enforced by the console for every action and by the browser for every top-level navigation, including ones a page starts itself (#508); per-app limits and budgets; purchase confirmation in delegated runs, with "Started by <app>" on the question | `mcp-security.spec.ts` (each classifier, instructions, "Started by"); `mcp-public-exposure.db.spec.ts` (nothing reaches the fabric before approval, the app cannot approve, exactly once, 2-minute window, a denial stands, allowed sites reach the fabric); `runner.db.spec.ts` (blocked navigations become steps); `tests/e2e/remote-control.e2e.mjs` (a page redirecting itself off the allowed sites is blocked in real Chromium); `mcp-apps`/`run-progress` specs (untrusted marking) |
| **A hosted model exfiltrating page content to its vendor** | **Inherent to using a hosted model.** Whatever a tool returns, the vendor sees. `browser:drive` is an opt-in for exactly this reason: delegating (`run_goal`) returns the run's answer, not the pages; driving returns the pages. Do not connect a hosted app with `browser:drive` to profiles whose content must not leave your machines | (none: a property, stated here and on the consent page) |
| **Exfiltration through tool arguments** (a page makes the model put data into a goal or a navigation URL) | Goals from an app are stored and shown verbatim in the run; navigation is limited by allowed sites; network-reaching JavaScript needs approval; the audit trail keeps the goal's first 200 characters and the URL host | `mcp-public-exposure.db.spec.ts` (audit row fields) |
| **A hosted app turning one approval into a standing one** (#555) | "Don't ask again" is accepted only from the signed-in web and Android app (channel and the request's credential); an app relaying the chat, an elicitation form or an MCP Apps card approves once; there is no tool or route that creates a saved approval; in a run an app started with "confirm purchases" on, the gate always asks, whatever rules exist | `dont-ask-again.db.spec.ts` (channels, the AI-app limit), `approval-rules.spec.ts` (no creating route or tool) |
| **A hosted app using the owner's saved logins** (E37.3) | A run an AI app starts gets the saved-login tools only if **all** hold: the app's limit `allowSavedLogins` (default **off**, set by the owner on the app's page), the task or chat's `useSavedLogins`, and both secrets switches (deployment and owner) with a connected Vault. The app never sees a login, a password or a code: it receives the run's answer; the runner passes a per-run reference and the fabric types the value, bound to the page's exact origin. A run that signed in and was not started from a chat keeps the confirmation before payments on (`unattendedPayments`, default `ask`), and a run that used a login lists it (`usedSavedLogins`). | `saved-logins.db.spec.ts` (the opt-in, the app limit, the marker test, the mismatch) |
| **A hosted app filling the owner's identity details** (E37.6) | A run an AI app starts gets `saved_identity` and `fill_from_identity` only if **all** hold: the app's limit `allowSavedIdentity` (default **off**, and it never widens `allowSavedLogins`), the task or chat's `useSavedIdentity`, saved logins usable and the grant's identity scopes. The app never sees a detail: it receives the run's answer; the model names a field and the fabric types it, or chooses the select's option, bound to the page's exact origin; a sensitive field (a date of birth, an ID number) only on a site the owner listed for that item, and only on `https`. What the fabric filled is not readable back (elements, text, scripts, pictures); the limit of that is stated in [secrets.md](secrets.md#identity-details-e376). No MCP tool lists or fills one. | `saved-identity.db.spec.ts` (the switches, the app limit, the marker test, the read-back filter) |
| **A hosted app paying with the owner's saved card** (E37.7) | A run an AI app starts gets `saved_cards`, `declare_charge`, `pay_with_saved_card` and `confirm_charge` only if **all** hold: the app's limit `allowSavedCards` (default **off**, and it never widens `allowSavedLogins`), the task or chat's `useSavedCards`, saved logins usable and the grant's card scopes. The app never sees a card: the model names a card by a per-run reference and the fields by target, and the fabric types them; **the owner approves each shop and amount** (a confirmation with the merchant, the card and the amount), a remembered approval needs a **required amount limit** and is bound to the shop and the card, and the app's **confirm purchases** limit makes every card use ask whatever is remembered. A run that is not started from a chat never types a card without `unattendedPayments: allow` and a matching remembered approval. A page that steers the agent to pay elsewhere gets a refused navigation or a refused card use (a wrong shop or payment frame warns the owner and switches cards off for the run). No MCP tool lists a card or pays. | `saved-cards.db.spec.ts` (the switches, the app limit, the per-shop approval, the limit, the injected page, the canary scan) |
| **A hosted app reading or sending the owner's mail, calendar or documents** (E39.7) | **No MCP tool lists, uses or changes a connection** (`mcp-manifest.spec.ts` asserts it). A run an AI app starts gets the connections the owner switched on (E50.17: every run does) only while the app's limit `allowConnections` is on (**on** by default for a new app since E50.17, an app saved before keeps its value; the owner turns it off on the app's page). The app itself never lists or calls a connection: its token reaches only `/api/mcp`, and no MCP tool takes or returns one. Reads are free; every call that sends, creates, changes or appends asks the owner on a **high-risk** card, which an OAuth app cannot answer (`answerable_here: false`) and which is built by the server from the validated arguments, so an app that relays the card cannot change what is approved; "Don't ask again" is ticked only in the signed-in web or Android app, covers one connection and one tool, and for mail and invitations only the approved recipients. What a connection returns is marked as the owner's data, never instructions. | `runner-connections.db.spec.ts` (the app without `allowConnections` gets no tool; injection scenarios), `mcp-manifest.spec.ts`, `chat-connections.db.spec.ts` |
| **Cost abuse** (an app starts many expensive runs) | Agent policy budgets; per-app runs at once, runs per day and spend per day, under deployment ceilings; rate limits on write calls | `connected-apps.db.spec.ts` (limits); `mcp-public-exposure.db.spec.ts` (writes per app) |
| **Denial of service** | nginx per-address limits on `/api/mcp`, `/api/oauth/`, `/.well-known/`; 1 MiB bodies; API limits per connection, per user and on unauthenticated `401`s (which fail closed when the limiter fails, while authenticated callers fail open) | `nginx-mcp-overlay.spec.ts` (`nginx -t`), `mcp-public-exposure.db.spec.ts` and `mcp-security.spec.ts` (each key at and over its limit) |
| **A hosted app reading or planting the owner's memories** (#551, #553) | No MCP tool reads or writes a memory; a memory proposal is not listed to an MCP client, reads as `404`, and an answer to one from an MCP channel is refused; the browser agent's `propose_memory` is refused unless the values come from the owner's own answers, so page text cannot plant one | `capabilities.json` (`memories.*`: MCP none), checked by `capabilities.db.spec.ts`; `memories-at-work.db.spec.ts` (MCP cannot read or answer a proposal; the injection case) |
| **A hosted app supplying a sensitive task value** (#552) | A sensitive parameter is never accepted from the API, the CLI or MCP (`400 SENSITIVE_INPUT`) and is never a field of the `form` an app may relay; it is asked as a secret in Hexactra once the browser opens. Every value is inserted into the goal as data and cannot change the run's allowed sites, policy or confirmation setting | `task-params.db.spec.ts` (sensitive refused, the marker grep, the injected value) |
| **A hosted app reading the owner's learned procedures** (E46.22) | `procedures_list` and `procedure_get` need the opt-in scope `procedures:read` (not ticked by default) and are listed and callable only while the Knowledge Graph's deployment switch **and** the owner's own switch are on; otherwise they are absent from `tools/list` and a call answers "turned off". A step list shows labels, targets and argument sources masked as in the run trace (a saved login by its label, a sensitive parameter by its name, never a typed value or a secret); labels can come from web pages, so the result starts with the untrusted notice and is marked `untrusted`. | **A hosted app running a learned procedure, or changing one** (E46.22) | `procedure_run` needs `procedures:run` (opt-in) and the same switches; it runs only an **active** procedure of a task in `reuse` mode, refuses a sensitive parameter, and starts the run through the run start path every run uses (the app's limits, the policy, the gates, the questions in the owner's Inbox), returning the run id at once. **No tool creates, edits, approves, declines, restores, forgets, exports or imports a procedure, or changes a switch**: an OAuth app cannot answer a review. Inside a run, a procedure called by the agent (`run_procedure`) runs every step through the same tool wrapper and gates, and cannot call another one. | `mcp-procedures.db.spec.ts` (with and without the scope, the Inbox question, no write tool), `mcp-manifest.spec.ts` (no tool that changes a procedure or a switch), `kgraph-procedure-tools.db.spec.ts` (gates, depth 2 refused) |
| **A hosted app reading or planting the owner's site facts** (E46.35) | `site_facts_list` needs the opt-in scope `site_facts:read` and `site_fact_propose` the opt-in scope `site_facts:write`; both are listed and callable only while the Knowledge Graph's deployment switch **and** the owner's own switch are on (otherwise absent from `tools/list`, and a call answers "turned off"). ### Consent with the Knowledge Graph off

With the Knowledge Graph's deployment switch off, its scopes (`procedures:read`, `procedures:run`, and any scope that only a feature-gated tool uses, such as E46.35's `site_facts:*`) are not in use. `mcp-kgraph-consent.db.spec.ts` proves each line below for a personal access token, a session and an OAuth app (E46.37, #893):

- **`tools/list` is the list of main** for each caller: the pinned manifest less the Knowledge Graph tools, compared on names, order, titles, hints and schema hashes. A direct call of a Knowledge Graph tool answers "turned off".
- **Not on the default consent screen, not granted by it.** The scopes are opt-in (`default: false`), so a client that asks for no scope (Claude and ChatGPT do) sees and gets the default scopes only.
- **Not shown as in use.** Not in the token, the platform's grants list, Connected apps or a card's `granted_scopes`. A personal access token or a session is shown the card scopes, which never include them.
- **Not offered by a step-up.** A call of a Knowledge Graph tool answers "turned off" (200), never `403 insufficient_scope`. Another tool's step-up challenge never names one. With the switch on, the same token is asked to step up, so the switch is what keeps them out.
- **Useless even when held.** A token explicitly granted them lists no Knowledge Graph tool. Its calls answer "turned off", and it cannot reach `/api/kgraph` (an `oat_` token is confined to `/api/mcp`).

**Not offered while off** (#916, on the platform's per-request scope availability, EnterpriseAppBase #1215, platform `0.1.0-next.40`): each Knowledge Graph scope registers with an `available` check (`src/mcp/mcp.scope-availability.ts`, bound to the Knowledge Graph's switches by `McpScopeAvailabilityBinder`). It fails closed: before the app is up, after it closes, or when the settings read throws, the scope is unavailable. While the deployment switch is off:

- The protected-resource metadata (`/.well-known/oauth-protected-resource/api/mcp`) and the authorization server metadata leave the Knowledge Graph scopes out of `scopes_supported`.
- `/authorize` drops them from the request. A request that asked only for them is refused with `invalid_scope`.
- The consent screen (`GET /api/oauth/requests/:id`) does not show them, and approving the request does not grant them. The other requested scopes are granted as usual.
- A token that already holds one (granted while the switch was on) gets no permission from it: the platform drops an unavailable scope when it resolves the token.

With a signed-in user (consent, token resolution) the check is the deployment switch and that user's own switch; with no user (the metadata documents, `/authorize`) it is the deployment switch alone. Turning the switch on offers the scopes again on the next request; nothing is cached.

## Hexactra as a server and as a client

This document is about Hexactra as an MCP **server**: hosted assistants call `POST /api/mcp`. Since E39.9 Hexactra is also an MCP **client**: the owner can add an MCP server as a connection and the agent can use its tools in a run ([connections.md](connections.md#mcp-servers-e399)). The two do not meet: no tool of this server lists, adds or uses a connected server, and a connected server's tools are never exposed back through this server. The threats are the mirror image. A hosted assistant is an untrusted *caller*; a connected server is an untrusted *callee* whose tool descriptions and results reach the model. The mitigations are the owner's per-tool decision (every tool off by default, `read` or `write`), a changed tool being switched off until reviewed, cleaned and capped descriptions plus the fixed instruction that they are information not instructions, a gated and validated `write`, redaction of credentials in both directions, and an outbound transport that checks every address at call time and never follows a redirect.

## What this does not cover

- **The redaction is a tripwire, not a guarantee.** A page can encode a token (base64, split across fields) and a script can rebuild one. The JavaScript tripwires (`fetch(`, `XMLHttpRequest`, `sendBeacon`, `document.cookie`, `localStorage`, `navigator.credentials`) are a string match: `window['fe' + 'tch']` passes them. `browser:evaluate` is a high-risk opt-in for that reason.
- **The sensitive-page rule sees the last element list.** Before the app lists a page's elements the console does not know it has a password field; a desktop click is always treated as outside the browser because the console cannot tell.
- **Personal access tokens are the owner's own credential.** They are rate limited, audited and can be switched off for MCP, but they are not asked for approval: an agent framework with a token runs with the owner's authority, as it always has.
