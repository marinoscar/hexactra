# Threat model: secrets the agent can use but never see (epic E37)

The agent can sign in from a saved login, fill identity details and pay with a saved card without the model reading the value (epic E37, #579; how it works: [secrets.md](secrets.md)). This page is the threat model of that feature: for each threat, **what stops it and what does not**. It is written to be read next to [security-hosted-clients.md](security-hosted-clients.md) (hosted AI apps) and the operator's [public-exposure runbook](runbooks/public-exposure.md#7-the-built-in-secrets-store-on-a-public-console-e375).

Read it as a statement of what the code does, not of what is safe. Everything below was checked against the repository; **none of it has been exercised against a real Vault, a real node and a real site yet** (the acceptance run of #597 is still to be done by the owner on a deployed stack: see [What has not been proven](#what-has-not-been-proven)).

## What is protected, and the rule that protects it

A saved login, an identity detail or a card number is **fetched and typed by the fabric** (the Rust control plane). The model names an item by a per-run reference and a field by its key; the fabric reads the page's origin from the browser at the moment of typing, asks the owner's provider with it, types the value with trusted input and wipes it. The value does not enter the console's database, a model's context, a step, a log, a span, a screenshot or an export. A provider that cannot be reached makes the agent ask the owner; it does not fail the run by itself.

That rule has two parts that can fail separately: **where the value may go** (the origin and the owner's per-item rules) and **who can reach it on the way** (the console, the fabric, the node, the provider). The table below takes them one threat at a time.

## Who and what is trusted

| Component | Trusted with | Why it must be |
|---|---|---|
| The owner's provider (their Vault, or the built-in store) | Every value | It is where they live. |
| The fabric (`hexactra-control`) | A value for the length of one typing action, in memory | It fetches and types; it holds no secret at rest. |
| The console | The **Vault path:** the owner's OAuth refresh token and the short-lived access token (never a login value; a key of an outside service the owner keeps in Vault, for each call the console makes to that service, E50.3). **The built-in store:** every value, as ciphertext in its database and, for a moment, in plaintext in its process. | It runs the connection and, for the built-in store, is the provider. |
| The node and its browser | The value while it is typed into the page | The page receives it; there is no way to type a secret without the browser having it. |
| The model | **Nothing.** Labels, names and masked usernames only. | It reads untrusted pages. |

## Threats

| Threat | What stops it | What does not |
|---|---|---|
| **A look-alike site** (`app.examp1e.test` for `app.example.test`) | The origin is read from the browser tab by the fabric when it types (never from model or page text), read once more just before typing, **checked again by the extension at the moment of typing** (the fabric sends the origin it verified as `expect_origin` on the `type` or `type_keys`; if the tab is no longer on it nothing is typed and the answer is `origin_mismatch`; for `type` the check also runs inside the page in the step that sets the value, for `type_keys` before every key, E37.10), and passed to the provider, which releases only to an **exact** match of the origin the owner saved (scheme, host, port; normalised: case, default port, IDN to punycode). A mismatch types nothing, ends saved logins for the run, and **asks the owner with a warning card** naming both hosts; the Activity list shows the refusal. A field in a frame of another site is refused (`cross_origin_frame`). A site-only match (same registrable domain, different origin) is shown to the model as not exact and refused. Sensitive identity fields and card numbers are refused on a page that is not `https`. | An owner who **saved the look-alike address as the login's site**. A page on the exact saved origin that an attacker controls in part (a user-content site). A compromised node or extension, which reports and enforces the origin itself (below). An extension older than E37.10 ignores `expect_origin` (the fabric's own two origin reads still apply); the value of a `type_secret` handoff, which the person gave and the fabric did not fetch, carries none. For `type_keys` the key in flight when a page navigates may still reach the new page (one character). |
| **A real page that steers the agent** (prompt injection from a page the agent is on) | Page text is data: the model's instructions say so; the tool set gives the model references, not ids or values; the page on screen decides what a lookup finds; a password is typed **at most once per run and site** and a code at most three times; a click on a payment or another commitment passes the **confirmation gate**, which decides by what is clicked and not by the model's words; the owner's per-task opt-ins (allowed sites, purchase confirmation) and Stop, takeover and the run record stay available; an unattended run that signed in keeps the confirmation before payments on (`unattendedPayments: ask`). A saved password is typed **only into a password field** (E37.10): before the provider is asked, and again right before typing, the fabric probes the target in the page and refuses (`target_not_password`: nothing fetched, nothing typed, the run asks the owner to sign in) unless it is an `input` of type `password`, or a text input that was a password input when the login was looked up or that has `autocomplete` of `current-password` or `new-password` (a "show password" toggle). A page on the right site that persuades the model to put the password in a visible text box on that same site (a comment, a profile field) therefore gets nothing. A card is released only under the per-merchant approval and amount limit ([below](#cards)). | **The check is on the password only:** a username, a code or an identity detail is typed into the element the model names, on the exact saved origin. **The probe reads the page's own attributes:** a page that lies about its inputs defeats it (that page is on the exact saved origin, and sees what is typed into it anyway), and a "show password" toggle on a site that sets neither `autocomplete` nor was looked up as a password input is refused, so the owner signs in. Saved logins plus a remembered approval plus a schedule can move money with nobody watching ([VISION §27](../../VISION.MD#27-human-emulator-full-powers-epic-366)). Allowed sites narrow where that can happen; they do not remove it. |
| **A hosted AI app asking for a secret** (ChatGPT, Claude, an agent framework) | No MCP tool reads, lists, saves or fills a secret, or connects a provider (`secrets.*` rows of `packages/shared/capabilities.json`, checked by `capabilities.db.spec.ts`; [parity.md](parity.md#what-secrets-added-e37)). `/api/secrets/*` is not part of any OAuth resource: an `oat_` token is confined to `/api/mcp`. A run an app starts gets the saved-login tools only with the app's limit `allowSavedLogins` (default **off**), `allowSavedIdentity` for details and `allowSavedCards` for cards, each its own limit that never widens another. The app receives the run's answer, not a value. The internal route the fabric calls is not reachable with a session, a personal access token or an OAuth token (the same `401`). | A hosted app can still **start a run that signs in** if the owner switched those limits on: it gets what the run does (the answer, the pages, if it has `browser:drive`), and it can aim the run at a site. Anything the page shows after sign-in is visible to a model whose output the vendor sees ([security-hosted-clients.md](security-hosted-clients.md)). |
| **A compromised console** (code execution in the API, or its environment and database) | A value is not in the console on the Vault path: it holds an encrypted refresh token and the short-lived access token, no login, password, code or card. There is no console route that returns a value. | **Everything the owner opened to agents in their Vault.** An attacker in the console holds the refresh token (decryptable with `SECRETS_ENCRYPTION_KEY` from the same environment) and the client secret, can call Vault's agent API as Hexactra, and Vault is told the `origin` by its caller and cannot see the browser: **origin binding is enforced by the caller reading the browser, not by Vault.** One field per call and a per-minute limit slow this; Vault's activity page and its owner notices record it. **On the built-in store it is worse:** the console holds `SECRETS_STORE_KEY`, the wrapped data keys and the ciphertext, so a compromised console reads every owner's saved logins. This is why the Vault path is recommended for more than logins ([secrets.md](secrets.md#choosing-a-provider)). |
| **A compromised node** (the machine that runs the browser) | The node never holds a provider token or a key; it cannot ask Vault. It receives a value only inside one typing action the control plane sends it, for the page the fabric believes is on screen; nothing secret is stored on it by Hexactra ([docs/nodes.md](../../docs/nodes.md#what-a-node-holds-of-a-secret)). Stop and takeover work. | The node **reports the tab's URL**, and the fabric trusts it: a node that lies about the origin gets the value for a site of its choosing, typed to it. The value is in the node's ordinary process memory (the host agent, the native host, the extension) while it is typed, and is not wiped there. The node already holds the owner's signed-in profiles, so this adds to a compromise the owner already has; it is why the node is the owner's own machine, with full-disk encryption. |
| **A stolen database backup** | **Built-in store:** values are AES-256-GCM ciphertext under a per-owner data key that is wrapped by `SECRETS_STORE_KEY`, which is not in the database; the backup holds ciphertext and wrapped keys only (a test scans the database for a seeded marker). **Vault path:** the backup holds the refresh and access tokens encrypted by the credential store (`SECRETS_ENCRYPTION_KEY`, also not in the database), the connection's address, client id and last error **code**, and the value-free Activity rows. | A backup **together with** `infra/compose/.env`: the keys are in the second file, which is why the runbook says to keep the two apart. The ciphertext binds the owner but not the item or the field (Vault's crypto port gives no such context, vault#227). Activity rows reveal which sites the agent signed in to and when (host only, never a path or a value). |
| **A stolen provider token** (the access token the fabric holds, or the refresh token) | The access token is short-lived, held in the fabric's memory only, and dropped at expiry; it is scoped (`vault:items_read`, `vault:items_fill`; `items_write` and the identity and card scopes only when the owner granted them) and it reaches only logins the owner opened. The refresh token is in the console, encrypted, and the owner revokes the grant in Vault's **Connected apps** or with **Disconnect** (which revokes at Vault and deletes the tokens). Vault's own deployment kill switch and Hexactra's two switches stop use at once. | Use of the token until it expires or is revoked, for every login opened to agents, by whoever holds it. |
| **Replay of a refresh token** | Vault rotates the refresh token on every use and, when a used one is presented again, **revokes the whole grant**. The console takes one refresh at a time per connection (a process-local single flight and a database lease), stores the new token **before** using the new access token, and, if it cannot store it, marks the connection `needs_reconnect` rather than carry on with a token Vault already retired. The owner is notified once and runs fall back to asking. | A thief who replays first leaves the owner disconnected (a denial, not a disclosure); the owner reconnects. The console cannot tell a replay by an attacker from its own crash between two writes: both end the same way. |
| **A crash around a payment** | Each field's phase (`typing` before, `typed` after) is saved in the run's record before the next one; a retried job does not type a typed field again and **never types a password that may already have been typed a second time**. For a card, the phases surround the pay click: a job that dies around the click leaves the payment `unknown`, a second click is refused by the gate and asks the owner, and no saved approval applies to it. | Crash safety is **minimal** (#584, the general version, is not built): a real process kill on the deployed stack has not been exercised. A payment the page took before the crash may be charged twice by the site's own retry. |
| **A hostile payment frame** | A card field inside a cross-origin payment frame is typed by a click and keystrokes at screen coordinates, so no script of ours runs in the frame; the fabric reads the top-level origin (the merchant) and the frame's origin and the provider checks the frame against the merchant grant's list; a frame whose origin cannot be determined (`about:blank`, `data:`, not `https`) is refused and nothing is fetched. Login and identity fields are still refused inside frames. | The frame origin is what the page declares for the frame element. A frame that redirects to another site, or a frame inside a frame, is not seen. The protection that remains is the owner's merchant grant, its amount limit and the audit trail, and a virtual card with its own limit from the bank. |
| **A password the owner typed, kept so it can be saved** (E37.4b) | The console never has it: the owner types it into the `credentials` card, the console passes it on to the fabric in the one answer call (single use, as for every sign-in) and the **fabric** keeps a zeroizing copy **only** for a handoff the runner opened with `offer_save` (only when the owner's provider can save: the built-in store, or a Vault that can), after the agent types it, until it is used, **ten minutes after the owner gave it**, or a restart; it is never persisted, returned, logged or put in an event or an audit row. On Save the fabric sends it to the provider's create route (Vault: purpose `save_login`; the built-in store: its internal `save` route, authenticated with the owner-bound `sct_` credential, #712) and answers only that it did; the card is answerable only in the signed-in web and Android app (a hosted app, webhook, notification action, MCP client, CLI or other REST caller is refused, declining included); the owner presses it, and edits the name, so a page that makes the model call `propose_saving_login` gets a card, not a save; the site and origin on the card are the fabric's and the console's reading of the tab when the password was typed, never the model's words; a sign-in is offered once, never when the page still shows a password field, never for a saved-login sign-in, and never for a site the owner chose "Never for this site" for. One save at a time; a taken name or an unreachable Vault leaves the copy for a retry, success wipes it. A test scans every table of the console's database for a marker password after a save and finds none, and the fabric's events and logs and the answers of the route are scanned too. | **The copy outlives the browser session** (the run usually ends before the owner decides), so for ten minutes a compromised fabric process or one that can read its memory holds a password the owner typed, where before it held it for one typing action: this is the cost of letting the owner decide after the run. A compromised console can create a save question for any handoff of its owner and press Save itself (it is the service holding the fabric's token): it still never reads the password, but it can make the fabric save it under a name and origin of its choosing, bound to the origin the console names (the fabric checks only that it is a usable page origin). The origin is the console's reading of the tab; a page that navigates the tab between the typing and that reading moves the origin. A Vault that is not at contract 1.3 refuses the purpose. **With the built-in store the password crosses the console's Node process once more on Save** (the fabric posts it to the store's `save` route; it is taken into a buffer zeroed after the call, but Vault's create service encrypts it from a string the garbage collector frees later), the same residual as the store's release path. |
| **An administrator reading users' secrets** | No route returns a value to anyone. The administrator's page shows counts only (owners connected, owners to reconnect, fields typed and refusals this week) and never a user, a site or a login. The `secrets:read_any`-style permissions of Vault are **not declared** in the console, so no role can hold them (every role is walked in `secrets-store.db.spec.ts`). A user's Activity is theirs. | **Someone who controls the deployment** (the host, the database and `.env`) can read the built-in store, and on the Vault path can use the connection as described under a compromised console. An administrator who sets the **default Vault address** decides which Vault owners connect to; the owner still sees that Vault's own consent screen, but a Vault of the administrator's choosing learns **which sites the agent looks logins up for**. |
| **Logs, traces and exports** | The OAuth callback's query is kept out of the request log, out of traces and out of nginx's access log; the fabric's audit events (`secrets.lookup`, `secrets.release`) carry the field **name**, the origin, the purpose and the outcome, never a value or its length; the console copies a whitelist of those fields into `secrets_activity` and drops the rest (a test seeds markers in every place a value could leak and scans the table and every response). A step and a run record the item's name, the **label** and the masked username. What the fabric filled reads `[filled from your saved details]` when the model reads it back, a box covers it in every screenshot the model is shown, and the run trace's pictures are masked at capture. The run export is masked again at export time. Canary tests scan the fabric's tracing feed at debug level, every operation, the event log and the state database for seeded canary values. | The masking of **text** is by pattern (card, account and ID-number shapes, [E35](runs.md)): a value in a shape no pattern knows is not masked. A page that **copies a filled value elsewhere** (a "review your answers" panel, a confirmation line) shows it in text the fill record does not know to hide; Logs of the provider, the site and the network are outside Hexactra. OpenTelemetry traces of agent runs (#585) are not built, so nothing was checked there. |
| **A page reading back a typed value** | The same read-back filter as above for `observe_elements`, `read_text` and `run_javascript` that reads a value; trace pictures masked; no desktop picture while a filled input is on the page; no screenshot at all while a value is in flight (the fabric refuses one). | A script of the page itself reads its own input: the site always sees what is typed into it. That is the trust boundary of signing in (VISION §11.6). |
| **The agent reading back a secret it typed** (a handoff code or password, E49.3 #960) | The extension remembers every value it typed with a sensitive `type` or `type_keys` (at least 4 characters), in the service worker's memory only, for ten minutes, at most twenty. It replaces each with `[secret]` in `evaluate`, `text` and `elements` results and in every error, before the result leaves the node (`apps/chrome-extension/src/typed-secrets.ts`). That covers a whole occurrence anywhere in the result, and a value read **one box at a time** (short strings that, in order, spell it out). | A script that **transforms** the value before returning it (reverses it, sums the digits, encodes it). A value of 1–3 characters. A page that shows the value in a **screenshot** the model is shown. The value is gone from memory after a service-worker restart. A complete fix would cut `run_javascript` off from typed fields, against the owner's full powers ([VISION §27](../../VISION.MD#27-human-emulator-full-powers-epic-366)). A 4–6 digit code can also match an unrelated number on the page for those ten minutes (it reads `[secret]`). |
| **A page that shows its own sign-in code to the owner (QR sign-in hijacking, #924)** | A scan question shows the owner a live picture of what is on the node's screen, so a page could try to have the owner scan **an attacker's** sign-in QR code with their banking or messaging app, which would sign the attacker in. The picture and the address are the **server's**: the console captures the picture through the fabric and reads the tab's address from the browser when the question opens, never from the model, the asker or the page's text; every picture is checked against that address again and a tab on another site gets no picture ("Do not scan"); the card names the site in a warning that cannot be switched off ("Only scan this if you just started a sign-in to …"); the picture is shown only on the signed-in web, Android app and Inbox, never in a notification, a webhook, an AI app or MCP, and never stored; the code is never decoded or relayed as text. | **A page on the right site** can still show a code that is not the one the owner expects (a compromised or hostile page of that site), and a page reached by the agent's own navigation is "the site the owner started a sign-in to" from the card's point of view: the warning asks the owner to scan only a sign-in they started, and that judgement is theirs. The address is what the node reports (see a compromised node). |
| **A code sent by text message or email** | A provider supplies **authenticator-app codes only**. A code that arrives by SMS or email is not in a vault: the run asks the owner (`code` request) as before. | Nothing. Say so to owners: a bank that only texts a code still needs the owner. |
| **Server-side release of a key of an outside service** (E50.3, #973) | **Who can ask:** only the console API process, from the service credentials port, at the moment of a call to that service (web search). Not the fabric (its routes refuse kind `api_key`), not a tool, not a model, not an MCP client (no route returns a key). **What binds the request:** the owner (the run's or request's own principal), the `service` and the `name`, chosen by the console's code from the deployment's settings, never by a model or a page; Vault's own per-item opt-in (`agentAccess = fill`), its 120-a-minute limit per owner and service, and its audit row (`agent.service_key.read`); the deployment's `secrets.agentUse` switch, read before the 60-second in-memory cache; the remote Vault needs the separate scope `vault:service_keys_read`. A release and a refusal are rows of the owner's Activity, without the value. | **A compromised console gains every service key its owners opened to agents**, from the built-in store directly and from a remote Vault through the owners' grants that carry `vault:service_keys_read`, exactly as it gains logins today; and it gains the keys of the console's own credential store anyway. The value crosses the console's process for every call (it makes the call), as a string and a buffer that is wiped, and stays cached for up to 60 seconds. Vault cannot tell the console's call to the search provider from a call by an attacker in the console. |
| **A provider that is down, slow or refusing** | Every provider failure becomes an instruction to the model ("Saved logins are not available right now. Ask the owner to sign in") and the sign-in card; the run continues after the owner answers. The connection's state follows the outcome (`needs_reconnect`, Vault's agent access off). | The run waits for a person; in an unattended run that is a stalled run until someone answers. |

## Cards

Cards are **stricter than logins, because a card works on any site**: a site binding cannot protect it, so the protection is the owner's decision per merchant and per amount, in two places the model cannot reach.

- **The provider's merchant grant.** Vault lists a card only for a merchant it holds a live grant for (maximum amount and currency, optional payment frames, a period limit, an expiry, and whether the security code is included, off by default). A runtime cannot create or widen one. There is no list of every card.
- **Hexactra's per-merchant approval with an amount limit.** The first payment at a merchant always asks the owner (the merchant's host, the card by brand and last four, the amount and what is bought). A remembered approval needs a **required amount limit**, is bound to the merchant's registrable domain **and the card**, and never matches a plain click; the site-wide "Press Pay" rule never covers a card. **No rule covers every merchant.**
- A charge is declared (`declare_charge`) before anything is typed, with the merchant host taken from the browser, never from the model; the amount must fit the grant and, if the task has one `money` parameter, that ceiling. The security code is typed last, only if the grant includes it. A run that is not started from a chat types a card only with `unattendedPayments: allow` **and** a matching remembered approval with a limit; an AI app's **confirm purchases** limit always asks.
- A bank's verification step (3-D Secure, an approval in the banking app) is never passed: the run asks the owner with the question kind `verification`.

**What does not stop it:** a card typed at a merchant the owner approved, for an amount under the limit, if the agent was steered into buying something else there; `confirm_charge` compares the amount the model read on the page, a check of the model's reading and not of the shop; a hostile payment frame (above); the owner's own card at a merchant that stores it; a stolen card number from the provider, which is the provider's threat model, not this one. Prefer a virtual card with its own limit, and a shop where the card is already saved in the shop's account in the node's persistent profile (no card stored here at all). **Hexactra is not a payment service and claims no card-industry compliance (PCI DSS or similar).** The built-in store holds no cards.

## What has not been proven

- **No real run has happened.** Everything is tested against the fake Vault (`apps/api/test/support/fake-vault.ts`, `crates/hexactra-credential-resolver/src/fake_vault.rs`), an in-memory fabric in the console's tests and fake extensions in the fabric's. The acceptance session of #597 (a scheduled task signing in with nobody there, a look-alike address, Vault unreachable, a canary search of the logs, the export and the trace, and a real small purchase) has not been recorded; follow-ups are filed on the epic.
- **The browser-side origin guard and the password-field check (E37.10) have not run in a real Chrome.** They are tested in the fabric against a fake extension that applies the same comparison, in the extension's tests (the page function and the guard, in jsdom, with a mocked `chrome` API) and by running the probe script in jsdom against inputs of each kind; no real site, with a real toggle or a real navigation, has been tried.
- **The general harness safety work is not built:** a fast Stop that cancels a model call (#582), pause (#583), crash safety after every action (#584) and an OpenTelemetry trace per run (#585). The saved-login path has the minimal per-field phase record described above.
- **Whether Vault's behaviour matches its contract** is taken from its documentation (`agent-credential-api.md`, contract 1.2, beta); the shapes are mirrored in `vault-contract.ts` and in Rust, not imported from the published contract package.
- **Pattern-based masking** and the **read-back filter** are best effort and say so.
